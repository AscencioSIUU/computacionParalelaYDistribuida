01 · De pseudocódigo a C real

Un programa, tres modos de ejecución

El diseño se llevó a C + OpenMP en un solo archivo (climate_sim.c) que comparte el modelo de predicción y expone tres modos por línea de comandos:

  • seq — bucle secuencial, un solo hilo
  • pfor — #pragma omp parallel for, paralelismo de datos
  • sections — #pragma omp sections, paralelismo de tareas

Escalamiento del problema

Con solo 500 regiones el cálculo es demasiado pequeño para medir nada real. El modelo se itera repeat veces por región (afinamiento sucesivo del pronóstico), así el trabajo total N × repeat escala sin disparar la memoria.

02 · Código real

Versión secuencial

static double ejecutar_secuencial(long n, int repeat, ...) {
    double sumaTemp = 0, sumaHum = 0, sumaViento = 0;

    double t0 = omp_get_wtime();
    for (long i = 0; i < n; i++) {
        double Tp, Hp, Vp;
        predecir(temp[i], hum[i], viento[i], repeat, factorAjuste, &Tp, &Hp, &Vp);
        tempSig[i] = Tp; humSig[i] = Hp; vientoSig[i] = Vp;
        sumaTemp += Tp; sumaHum += Hp; sumaViento += Vp;
    }
    double t1 = omp_get_wtime();
    return t1 - t0;
}

omp_get_wtime() rodea únicamente la lógica de cómputo — igual en las tres versiones, para que el tiempo sea comparable.

03 · Código real

Paralelismo de datos — parallel for

    double t0 = omp_get_wtime();
    #pragma omp parallel for \
        shared(temp, hum, viento, tempSig, humSig, vientoSig) \
        firstprivate(factorAjuste) \
        reduction(+:sumaTemp, sumaHum, sumaViento) \
        schedule(static)
    for (long i = 0; i < n; i++) {
        double Tp, Hp, Vp; // privadas: declaradas dentro del cuerpo paralelo
        predecir(temp[i], hum[i], viento[i], repeat, factorAjuste, &Tp, &Hp, &Vp);
        tempSig[i] = Tp; humSig[i] = Hp; vientoSig[i] = Vp;
        sumaTemp += Tp; sumaHum += Hp; sumaViento += Vp;
    }
    double t1 = omp_get_wtime();

Las cuatro cláusulas del diseño están presentes: arreglos shared, Tp/Hp/Vp privadas por bloque, factorAjuste como firstprivate y las tres sumas con reduction.

04 · Código real

Paralelismo de tareas — sections

#pragma omp parallel sections shared(...) firstprivate(factorAjuste)
{
    #pragma omp section
    for (i = 0; i < n; i++) { predecir(...); tempSig[i]   = Tp; }

    #pragma omp section
    for (i = 0; i < n; i++) { predecir(...); humSig[i]    = Hp; }

    #pragma omp section
    for (i = 0; i < n; i++) { predecir(...); vientoSig[i] = Vp; }
}
Solo hay 3 secciones — sin importar cuántos threads se pidan, como máximo 3 pueden trabajar simultáneamente en la fase de predicción. Esto se ve directamente en los resultados.

09 · Gráfica

Curva de Speedup

La diagonal gris es el speedup ideal (Sp = p). parallel for se acerca a esa línea sin tocarla — esperado, por el overhead de agendar y combinar el reduction.

sections se estanca en ~0.7×: su techo es 3 tareas, no la cantidad de threads.

Con 500 regiones y un cálculo trivial, crear/administrar threads cuesta órdenes de magnitud más que el cómputo real: Sp ≪ 1, tal como predecía el diseño (sección 40-41 del README). No es un bug del código — el problema es demasiado pequeño.

11 · Cuello de botella detectado

sections no escala más allá de 3 threads

La eficiencia de sections cae abruptamente: pasa de 73% (1 thread, secuencial disfrazado) a ~9% con 8 threads.

La causa no es sincronización costosa — es que el paralelismo de tareas está limitado por el número de tareas (3), no por el número de threads. Threads 4-8 quedan ociosos durante la fase de predicción.

La caída de 74%→60% es el costo esperado de repartir y recombinar (reduction) más trabajo entre más threads — no un error de diseño. Sigue siendo speedup real y creciente (0.72× → 4.77×), solo con rendimientos marginales decrecientes.

13 · Conclusión

¿Se logró la optimización esperada?

Sí, con carga suficiente

parallel for alcanzó 4.77× de speedup con 8 threads sobre N=3,000,000, con resultados idénticos a la versión secuencial.

Cuellos de botella detectados

  • sections: limitado a 3 tareas, no escala con p > 3
  • N=500 original: overhead de threads >> cómputo, Sp ≪ 1
  • Eficiencia decreciente en p=8 por overhead de reducción/agendamiento

El experimento confirma la hipótesis del diseño: el paralelismo de datos escala con el tamaño del problema; el paralelismo de tareas escala con el número de tareas independientes, no con el hardware disponible.
